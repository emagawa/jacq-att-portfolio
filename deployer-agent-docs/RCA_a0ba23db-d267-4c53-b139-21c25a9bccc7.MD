# RCA — jacqmagawa.com: /robots.txt & /sitemap.xml return homepage HTML

**Deployment:** portfolio-site-241 (`15f8ede7-...`) · active run `a0ba23db-d267-4c53-b139-21c25a9bccc7`
**Frontend type:** Cloudflare (static files uploaded to R2, served by a Cloudflare worker; `/api` proxied to the k8s backend)
**Template:** fastapi_react_mongo_shadcn_base_image — but this app is a **static vanilla HTML site**, served via a custom `build-frontend-artifacts.sh` override.
**Scope:** Debug only. No redeploy performed, per request.

---

## 1) How the frontend static files are served/built in production

**Build/upload (which directory is uploaded + the de-facto allowlist):**
The active override `build-frontend-artifacts.sh` (read from GCS) does **not** run `yarn build`. It cherry-picks a fixed set from the repo root into `/tmp/frontend-build` and `s5cmd sync`s that to R2 at `{bucket}/{DEPLOYMENT_NAME}/{TAG}/build/`:

```
cp index.html  -> staging
for d in css js assets: cp -r $d -> staging   # only if present
```

So the **effective allowlist is hard-coded in this script**: only `index.html` + the `css/`, `js/`, `assets/` directories are uploaded to R2. There is no extension filter — it is an explicit per-item copy. **Any other repo-root file is excluded from the artifact** (confirmed in source: `robots.txt`, `sitemap.xml`, `googlee2baf0cc1b65fae8.html`, `admin.html`, `*.md` all present at root, none staged).

**Serving + SPA rewrite:**
The Cloudflare worker serves R2 objects by exact key and falls back to `index.html` (HTTP 200) for any key it cannot find. Verified live:
- Exact-key hits work with correct content-type: `/css/style.css` → `200 text/css`, `/js/main.js` → `200 application/javascript`.
- Missing keys fall back to the homepage: `/robots.txt`, `/sitemap.xml`, `/about`, `/googlee2baf0cc1b65fae8.html` all → `index.html` with **HTTP 200** (the 65507-byte homepage, `content-type text/html`).

## 2) Why /robots.txt and /sitemap.xml are not served — PROVEN

They exist in source at repo root (`robots.txt` 93 bytes, `sitemap.xml` 266 bytes) but are **excluded from the R2 build artifact** because `build-frontend-artifacts.sh` only stages `index.html` + `css/`, `js/`, `assets/`. With no `robots.txt` / `sitemap.xml` key in R2, the worker returns its SPA fallback (`index.html`, 200).

**The platform does NOT intercept these paths.** This is purely an artifact-content problem — the files were never uploaded. (Same reason `/googlee2baf0cc1b65fae8.html`, the Google verification file, also returns the homepage.)

Content note (separate, minor): the source `robots.txt` points `Sitemap:` at `https://jacqmagawa.com/api/sitemap.xml` (a backend route), not `/sitemap.xml`. Worth reconciling once the static file is actually served.

## 3) Nested pages — /about/, /about, /about.html

- **For ANY file to be served, it must be an exact R2 key**, which means `build-frontend-artifacts.sh` must stage it. Today neither `about/` nor `about.html` exists in source, and even if added they would NOT be uploaded, because the script only copies `index.html` + `css/js/assets`.
- `/about.html`: once `about.html` is in the repo **and** staged by the build script, it will be served by exact-key match (this path is PROVEN — it is exactly how `css/style.css` and `js/main.js` serve today).
- `/about/index.html` for the URLs `/about/` and `/about`: **UNVERIFIED.** Whether the worker does directory-index resolution (append `index.html` to a trailing-slash path, or resolve a bare `/about` to `about/index.html`) is **Cloudflare-worker behavior that is platform-managed and not part of the manifest set I can read.** What I can prove is only that `/` maps to `index.html` (root directory-index works). I cannot confirm trailing-slash or bare-path resolution for subdirectories. Recommend validating this with a live test after the first multi-page deploy, or avoiding the ambiguity by shipping explicit `.html` files.

## 4) Custom 404 vs forced SPA fallback — PROVEN

The SPA fallback is **forced** by the worker: every unknown path returns `index.html` with **HTTP 200**, never a 404 (confirmed on 4 distinct missing paths). A true custom 404 page is **not achievable** through this serving layer as observed — the fallback always serves the homepage with 200. This is platform worker behavior and is not configurable through the app's manifest set (Dockerfile.cloudbuild / entrypoint.sh / nginx.conf / build-frontend-artifacts.sh / config.yaml); nginx.conf is not in the serving path for a Cloudflare frontend.

## Recommended fixes

### Fix A (primary) — upload ALL static files to R2. Edit `build-frontend-artifacts.sh`.
Replace the hard-coded cherry-pick with a full copy of the static root (minus app/infra dirs) so root files and future multi-page HTML are always included. Example staging block:

```sh
# stage everything at repo root except backend/build/infra dirs
cd "${SOURCE_DIR}"
rsync -a --exclude 'backend' --exclude 'frontend' --exclude 'node_modules' \
  --exclude '.git' --exclude '.emergent' --exclude 'memory' --exclude 'pip-cache' \
  --exclude 'etc' --exclude 'bluehost' --exclude '*.md' \
  --exclude 'Dockerfile.cloudbuild' --exclude 'entrypoint.sh' --exclude 'nginx.conf' \
  --exclude 'build-frontend-artifacts.sh' --exclude 'deploy.sh' \
  ./ "${STAGING_DIR}/"
```
(If `rsync` is not on the build image, enumerate `index.html robots.txt sitemap.xml googlee2baf0cc1b65fae8.html` + any new `*.html` and the `css js assets` dirs explicitly.) This fixes `/robots.txt`, `/sitemap.xml`, the Google verification file, and enables `/about.html`, `/projects.html`, etc. by exact-key serving.

### Fix B (multi-page structure)
Prefer explicit `.html` files (`about.html`, `projects.html`) — proven to serve by exact-key match. If using `about/index.html`, validate `/about/` and `/about` resolution live after deploy (worker directory-index behavior is unverified).

### Fix C (content, minor)
Update `robots.txt` `Sitemap:` to `https://jacqmagawa.com/sitemap.xml` once the static file is served.

### Not changeable
The forced SPA fallback (unknown path → `index.html` 200, no custom 404) is Cloudflare-worker behavior outside the app's manifest set — escalate to Emergent support if a real 404 status is required.

**Note:** `build-frontend-artifacts.sh` exists both as a GCS manifest override (what the build actually reads) and as a mirror at the repo root. The build uses the GCS override — the fix must land there (via the deployer/manifest path on the next redeploy), and the repo copy should be kept in sync.
